# 大厂 Git 协作规范的可视化指南

## 一、 🌳 分支命名与用途

用固定前缀明确分支职责，做到“一眼识用途，合并零误解”。

- **`master`** (生产主干) 👑：只存放最稳定、随时可上线的代码。
    
- **`develop`** (开发主干) 🛠️：日常开发主线，承载所有新功能的迭代。
    
- **`feature/*`** (功能分支) ✨：用于开发单一需求（例：`feature/user_login`），一需求一分支，互不干扰。
    
- **`test/*`** (测试分支) 🐛：专供测试同学寻找和验证 Bug。
    
- **`release/*`** (预发分支) 🚀：作为上线前的最后彩排与验证。
    
- **`hotfix/*`** (急救分支) 🚑：线上 Bug 的紧急修复通道，修复完毕需同步合并回主干。
    

---

## 二、 🌐 分支与部署环境映射

权限和环境明确对应，从源头减少把未测试代码发到线上的事故风险。

|**分支前缀**|**对应环境标识**|**适用场景 / 环境说明**|
|---|---|---|
|`master`|**PRO** (生产环境)|面向真实用户，只进绝对稳定的代码。|
|`release/*`|**UAT** (用户验收环境)|上线前的预发布与最终验收。|
|`feature/*` & `test/*`|**FAT** (功能测试环境)|开发自测、测试同学验证新功能。|
|`develop`|**DEV** (开发环境)|研发团队内部联调与开发迭代。|
|`hotfix/*`|**紧急修复**|针对 PRO 环境出问题时的临时急救。|

---

## 三、 📝 提交信息 (Commit Message) 规范

告别满屏的 “update”，让代码历史像说明书一样清晰。

**标准格式**：`<类型>: <描述>` _(注意冒号后有空格，例如：`feat: 添加用户登录功能`)_

- ✨ **`feat`**：新增功能 (Feature)
    
- 🐛 **`fix`**：修复 Bug
    
- 📚 **`docs`**：仅修改文档或注释
    
- 💄 **`style`**：调整代码格式（如空格、缩进，不影响代码逻辑）
    
- ♻️ **`refactor`**：代码重构（不增加新功能，也不修复 Bug 的代码优化）
    

---

## 四、 💡 单次提交“小原则” (最佳实践)

1. **单一职责**：一次 Commit 只做一件事（切忌把改 Bug 和做新功能混在一起提交）。
    
2. **控制规模**：单次提交修改的文件建议**不超过 13 个**。
    
3. **本地自测**：提交前务必在本地跑通代码。
    
4. **清晰可溯**：提交信息写清楚，方便未来排查问题或代码回滚。
    
5. **推前变基**：在 Push 代码到远程前，先 `rebase` 最新代码，有效减少分支合并冲突。
    

> **🌟 核心理念：**
> 
> 规范不是束缚，而是团队协作的超能力。用好这套规范，能大幅降低沟通成本和线上事故率，让每一次提交都成为代码的高光时刻！
